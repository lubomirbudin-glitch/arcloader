1What mmMover does

mmMover backs up camera cards. It reads the card only once and writes every block of data to all selected destination disks at the same time. Then it reads the copy on each disk back and compares checksums — with proxies (since 0.6.0) the primary disk is verified while the proxies are made, without an extra read. A card has two states: Safe to eject as soon as everything is written, and Safe to format only once everything is verified on all disks.

What happens to each card

  1. Copy to all destinations at once, into the folder <destination>\<date>\<card>\. The card's folder structure stays the same, and the files' modification date and time are the same as on the card.
  2. Verification: every file is read from every destination disk and its blocks are compared with the checksums computed while reading the card. The data is read from the disk, not from the computer's memory (both writing and reading bypass the Windows cache). With proxies, the primary disk is verified during the proxies — ffmpeg reads the clips through mmMover and every block it reads is verified; the other disks are read in parallel in the background. A RAW clip (BRAW, R3D, ARRIRAW) is read and verified by mmMover itself before the maker's decoder runs, and the decoder then reads it from the disk again (not from memory) — so RAW is read from the primary disk twice. Without proxies, or when the destination does not allow it (a network drive), each disk is read back right after the copy.
  3. Report into the _REPORT folder on each destination: HTML, PDF, JSON, TXT and a checksum list, plus ASC MHL in the ascmhl folder.
  4. Clip analysis (optional): technical details of every clip and three frames (first, middle, last) in the report.
  5. Proxies (optional): smaller .mov files for editing, with a LUT, burnt-in clip name and timecode, in the _PROXY folder.
Safe to eject × Safe to format As soon as all files are written to all disks, the job card shows the chip Safe to eject (neutral, not green) and the text “All files are on 2 disks — the card is safe to eject. Format it only after verification.” Clip analysis and proxies read only from the destination disks, so you can insert the next card in the meantime. But do not format the card until the second chip says Safe to format — only then is everything verified. Only Safe to format is green; the sound and the notification “mmMover: A001 done” with the text “Verified on 2 disks — the card is safe to format.” also come only then. Until then the chip shows Verifying…, and briefly Finishing verification at the end. When the decoder finds a defect in a camera file while making proxies (the copy still matches the card), a yellow label with the timecode and Preview appears; formatting is possible only after Checked — the card is safe to format.
Nothing is ever written to the card mmMover only reads the card. It creates, deletes and renames nothing on it. The same goes for the speed test in the Hardware window.

What else it does

  • Several cards in a row in the queue; while the proxies of one card are rendering, the next one is copying.
  • Built-in Log → Rec.709 LUTs for ARRI, Sony, Blackmagic, RED, Canon, Panasonic, DJI and Fujifilm, and automatic LUT selection by camera (chapter 6).
  • mmMover history: a “Backed up on …” line on the card, appending only new clips to an earlier backup, a folder name from the clip names, verifying a finished backup against ASC MHL and a free space check before the start (chapters 3, 8 and 10).
  • Output for production and editorial: a day report of the whole day, a CSV clip list (Resolve, Excel) and ALE (Avid), MD5 in addition to xxHash64, proxies ready for relinking in Resolve and Premiere (chapters 5, 6 and 7).
  • A USB connection check of the reader and disks with recommendations, and a bottleneck indicator during the copy (chapter 9).
  • The same on-disk format as the Mac version (still called Offload) — a copy made on Windows can be verified on a Mac and vice versa.
  • The command line bin\mmmover.exe for scripts (chapter 11).
  • While a job is running, mmMover keeps the computer from going to sleep.

2Installation and first start

Requirements

  • Windows 10 or 11, 64-bit.
  • Nothing else needs installing — .NET, FFmpeg (ffmpeg and ffprobe) and the Blackmagic RAW decoder are bundled.
  • The PDF report is printed by Microsoft Edge without opening a window; Edge is part of Windows.
  • Card copying, checksums, the report (HTML and PDF), thumbnails and proxies work right after unpacking.
  • Proxies on the graphics card: tested with NVIDIA. Without it, proxies are encoded on the CPU — slower, but they work.

Unpacking and starting

  1. Unpack the whole ZIP mmMover-win-x64-<version>.zip into an ordinary folder (e.g. Documents\mmMover). Do not run the app directly from the archive.
  2. Run mmMover.exe. The first start takes a few seconds longer (libraries are unpacked), later starts do not.
  3. On the first start Windows may show a blue window “Windows protected your PC” (if this is an unsigned build). Click More info → Run anyway.
A folder as an argument You can drag a folder with footage (e.g. a copy of a card on a disk) onto mmMover.exe. The app opens and the folder is already ticked in step 1 · CARDS.

Updates

mmMover downloads nothing and by default never checks for a new version. In Settings → App → Updates… enter the manifest address — a web address https://… or a path on a NAS or shared folder (e.g. \\NAS\mmMover\mmmover-update.json) from whoever prepares mmMover for you. The app then checks at most once every 24 hours (5 s after start) whether there is a new version; if there is, the link “New version 0.9.1” appears in the top bar. The window shows the release notes and where the new ZIP is. The Open button is shown only for an https://… address (opens the browser) and for a local folder or ZIP (opens File Explorer with the item selected). Network paths (\\NAS\…, a mapped network drive) and anything else are only shown as text to copy and open by hand (“Network path — copy it and open it by hand.”). The Check now button tries immediately: “You have the latest version …”, or “Cannot read the manifest: …” (it gives up after 5 s on a disk, 10 s on the web, and reads at most 64 KB). An empty address = the check is off.

Project

The Project drop-down in the top bar lists No project and the saved projects (the selected one is ticked), and below them Save as new project…, Rename… and Delete…. A project is a named set of settings — destinations, structure and checks (verification, checksum, name from clips, clip lists, day report), notifications and all proxy settings including the LUT, LUT rules and the proxy folder. What you change is saved into the currently selected project; switching to another one and back loses nothing. Jobs already in the queue took their settings when they were started — switching the project does not change them. While a start is being prepared (checks, questions) the switcher is locked. Tool paths, USB port names and the update check stay shared by all projects.

Save as new project… creates a project from the current settings and selects it; Delete… asks “Delete project Film X? The project's settings will be lost; the backups on the disks stay.” Name: 1–60 characters, must not repeat (not even in different letter case), and “No project” is reserved. The window title shows the selected project, e.g. “mmMover — Film X”. The project is written into the report and the history: the “next after A001 (today)” suggestion counts only cards of the same project, and the day report shows “Project: Film X” when all cards of the day come from it.

Appending to a card follows the project in which the card was originally backed up (not the one currently selected). When that project no longer exists (deleted or renamed), the append runs with the No project settings and the job card says so. The start checks only the LUTs and proxy folders that the jobs really use.

1 · CARDS

  • A card inserted into a reader appears by itself and is ticked (a card with a camera structure, or a non-empty card in a reader — e.g. from a sound recorder; this is turned off in Settings → Folder structure → Automatically select cards in readers as sources). While there is none, the step shows a dashed frame “Insert a card into the reader” (during an mmmover “Insert another card”).
  • The card tile shows the name, the camera (e.g. “ALEXA 35 · LogC4” — found from the card's first clip, read-only, at most 5 s; when mmMover does not recognise it, the label is missing) and the line “24 clips · 1.70 GB · exFAT · reader USB 3 · 5 Gb/s”. The connection type is “reader USB 3 · 5 Gb/s”, “reader USB 2.0”, “SD reader”, “NVMe”, “SATA” or “network”. Windows cannot tell Thunderbolt apart — a reader behind it shows up as NVMe or USB. A disk that does not look like a camera card additionally shows “does not look like a card” and is not ticked by itself. A card is a medium with folders such as DCIM, PRIVATE, CLIP, CONTENTS, XDROOT, M4ROOT etc., or with clips (.braw, .r3d, .mxf, .mov, .mp4, .ari, .crm…) at most one folder down.
  • Removable media and disks connected over USB or SD are offered. Neither the system disk nor a disk holding one of the destinations is offered as a card.
  • Under the card's details is a line from the offload history: grey “Checking whether the card is already backed up…”, then green “Backed up on 2026-10-06 08:15 to Backup (D:), Backup2 (F:) — verified, safe to format”, orange with the addition “· new files: 12 (3.2 GB)”, “— NOT VERIFIED (safe to eject, do not format)” or “…, but the card has changed since (4 files differ) — cannot append, only a full copy”, red “— with errors (3 files)”. A card mmMover has never copied gets no line; a card emptied in the camera shows a neutral “The card is empty — backed up earlier …”. mmMover recognises the card by the file system serial number and capacity, so even in a different reader; a reformatted card is a new card. The history is only on this computer (%APPDATA%\mmMover\history.json); a copy cancelled half-way is not written into it.
  • A ticked card has a Folder name field with a hint where the suggestion comes from. The grey pre-filled suggestion is: the reel from the clip names (A001C003_… → A001, “from the clip names (A001C003…)”); for a card without such names and without history, “next after A001 (today)” based on the cards copied into the same date folder; otherwise the volume label (for a folder, its name). Several reels on one card give no suggestion (“The card has more than one reel: A001, A002”). Two unknown cards get A002, A003 in turn. A name you type always wins. The suggestion is turned off by an option in chapter 5.
  • A card with clips added since the backup (and with the earlier destinations connected) has a yellow Append button (tooltip: “Append new clips only to the earlier backup (12 files · 3.2 GB)”). Pressing it ticks the card and, instead of the name, shows “Folder: 2026-10-06\A001 on 2 destinations”: only the new files are copied into the same card folder on the disks of the earlier backup (the Destinations step may be empty). It is not offered for a changed card, a different card, or a folder added by hand. Details in chapters 8 and 10.
  • The ⟳ button (“Reload connected disks”) reloads the disks and checks the destinations.
  • From folder… adds any folder (a copy of a card on a disk, a NAS, a card in a reader that the app did not offer by itself). It behaves like a card: it can be ticked and named.

2 · DESTINATIONS

  • Add disk picks a destination folder (the root under which the date folders are created). There can be any number of destinations; the app remembers the list (it belongs to the project).
  • A connected external USB disk is added by itself (the disk's root, e.g. G:\) and disappears from the destinations again when it is disconnected. A card or SSD from a camera (a camera structure right in the disk's root: DCIM, PRIVATE, CLIP, CONTENTS, ARRI, RED…, or clips right in the root as on an SSD from Blackmagic or Atomos), a card reader, or an internal or system disk (SATA, NVMe — even a disk behind Thunderbolt; add that one by hand) is never added as a destination. A backup disk with clips in folders is added, as is any disk with an mmMover (or older ArcLoader or Offload) backup. A disk you remove with the cross is remembered (by serial number and capacity) and is not added automatically again; Add disk or Forget removed disks (N) in Settings undoes that. A full disk (less than 1 GB free) or a read-only disk is not added — under the destinations it says in orange Disk BACKUP (G:) is full — not added as a destination. Nothing is added during the pre-start checks and in demo mode.
  • A destination tile has a number in a circle (in the report it becomes D1, D2…), the name, “7.20 TB free of 8 TB · NTFS · NVMe” and a space bar: grey for used, blue for what the selected cards will take (yellow when little space will be left after the offload, red when they do not fit — the sentence under the bar says why). The full path is shown in a tooltip when you hover over the name. The cross (“Remove destination”) removes the destination.
  • A disconnected disk has a red number and the text Disk not connected; while it stays like that, the offload cannot be started. The app checks the destinations about every 5 seconds, so the tile recovers by itself once the disk is connected.
  • A disk with exFAT or FAT32 shows in orange NTFS recommended — more reliable than exFAT/FAT32.
  • Without destinations you see the tip “Add two disks — every card is written to both at once.”; with a single destination, the warning Only one destination — two independent copies are recommended.
  • Under the destinations is a preview of the path the card will be written to, e.g. …\2026-10-07\A035_ARRI\ (the date depends on the option in Settings → Folder structure).

4Step by step: your first offload

  1. Connect the destination disks. External USB disks appear by themselves in step 2 · DESTINATIONS; add others (a network folder, an internal disk) with the Add disk button. Two independent disks are recommended. You only need to do this once — the app remembers the destinations.
  2. Insert the card into the reader. It appears in step 1 · CARDS and is ticked. There can be several cards at once; they are copied one after another. A card the app did not offer can be added with From folder….
  3. Check the card's folder name. The suggestion is pre-filled (the reel from the clip names, the next in sequence or the volume label). To change it (e.g. to A001), type the name into the Folder name field. The path preview under the destinations shows where the copy will go: …\2026-10-06\A001\.
  4. Check step 3 · AFTER COPY: Verification by reading back should be green (when off, it is yellow with a warning). If you want proxies, open Edit project, turn them on in the Proxies section and set them up (chapter 6).
  5. Start with the ▶ Start offload button or Ctrl+Enter. The started cards are unticked and a job card appears for each of them in the queue on the right.
  6. Watch the progress. The job card shows the phase bar (Copying · Verification · Proxies · Report), a large percentage of the current phase, the remaining time estimate, a speed table (Card read 661 MB/s · 1 RAID_A 661 MB/s · 2 SHUTTLE_B 661 MB/s) and the file being copied (“File 10 / 24”). Under the card is the Bottleneck line (chapter 9). You can Pause the job (chapter 8).
  7. Wait for the Safe to eject chip — everything is written and you can remove the card (the chip is neutral, not green). The green card “A001 — safe to format” with the sentence “All 24 files are on 2 disks and verified (xxHash64).” comes only after all disks are verified, and only then the sound plays and the notification arrives. Only now is the card safely backed up and can be formatted.
  8. Eject the card with the Eject card button. The card disappears from step 1, the reader stays connected. Insert the next card and continue from step 2 — the proxies of the previous card keep rendering in the meantime.
  9. When it is finished, the green card shows the summary with four values: Copy 602 MB/s, Verification 799 MB/s, Proxies 24 / 24 and Total 6 min 12 s, thumbnails of the first clips, and the app's button in the Windows taskbar flashes. Report PDF opens the report, Open folder the card folder on the first destination and Proxies the proxy folder. The card also appears under the queue in the TODAY overview.
Do not pull the card out early Do not disconnect the card until the job card shows the “Safe to eject” chip; do not disconnect the destination disks until it shows “Safe to format”. Do not format the card before the green “safe to format” card. If the job is cancelled or a file fails, the card is not backed up (chapter 8). When the app crashes or the PC turns off in the middle of a copy, after you insert the card it offers Finish interrupted backup — what is already on the disks is not copied again.
The same card again When you copy the same card (the same name) again on the same day, the new copy gets the folder A001_2, A001_3… An earlier offload is never overwritten.

How the copy works

  • The card is read once and the data goes to all destinations at the same time. A slower disk can lag behind for a while without slowing down the card read.
  • Both copy and verification can be Paused and then Resumed (chapter 8). The file in progress is first finished on all destinations (or read to the end during verification), and only then does the job stop; Resume continues with the next file. The time the job was stopped does not count towards the speeds in the report.
  • Reading and writing bypass the system memory (cache), and after writing the disk's cache is flushed too, so verification really reads the data from the disk. Volumes that cannot do this (some network ones) fall back to normal writing and the report says so for that destination: “Destination 1: the volume does not support direct writes; the system cache was used.”
  • A file in progress has the hidden name .<name>.offload-part on the destination and gets its real name only once it is completely written. An unfinished copy therefore never looks finished.
  • When a file on the card cannot be read, it is tried three more times. Then the file is marked as failed and the copy continues with the next file. A write error on one destination does not affect the other destinations.
  • System items (System Volume Information, $RECYCLE.BIN, desktop.ini, Thumbs.db, macOS files such as .DS_Store, .Spotlight-V100, ._*) are not copied; the report lists them as skipped.

What is checked before copying

Before anything is written, mmMover checks the following. When something is wrong, the job ends with the status Error and a message on the job card (meaning and solution in chapter 12):

  • the source exists and contains files; the destinations exist and can be written to;
  • no destination is on the same volume as the card, and no two destinations are on the same volume (that would not be a second copy);
  • the source is not itself an earlier offload (it has no _REPORT, _PROXY or ascmhl in its root);
  • every destination disk has enough space for the card, the proxies and the report — destinations on the same disk, the proxy folder and the cards already waiting in the queue are added up; proxies are estimated from the clip sizes, and before the proxies are rendered the space is recalculated from the real duration (when they do not fit, the proxies are skipped and the copy stays verified);
  • the card holds no names that Windows cannot store (the characters < > : " | ? *, names such as CON, NUL, a trailing dot or space), and no two files that differ only in letter case;
  • no file of 4 GB or more is to go to a FAT32 destination.

What is in the report

  • Header: card name, status label VERIFIED, COPIED — NOT VERIFIED or ERROR, start and end date and time.
  • Summary: number of files, data volume, number of clips and their total duration, copy and verification time and speed, checksum (XXH64, or XXH64 + MD5). When the job was paused, there is also “paused · not in the speeds” — the pause time does not count towards the times or speeds. A repair report (Copy again, chapter 8) has “repair (generation 2)” in its header.
  • Destinations: a table of disks — disk, folder, file system, number of files OK and errors. Below it the source and its file system.
  • Errors (only when there are any): the file and the problem, separately for the card and each destination — e.g. “destination 2: checksum mismatch (destination …, card …)”, “size mismatch: …”, “write failed”. In offload_report.json they keep their fixed English codes (shared with the Mac version).
  • Clips: for each clip three frames, the name (for camera proxies “(camera proxy)”), the path on the card, format and codec, resolution, FPS, duration, timecode, number of audio channels, size and proxy status (done, error, unsupported, skipped). FPS is the capture frame rate from the metadata of the clip's first frame; when it differs from the file's playback rate (off-speed, S&Q), both are shown on two lines: “35 fps” and below it, smaller, “playback 24”. The capture rate is known for ARRIRAW (via art-cmd), Blackmagic RAW, RED (via REDline; playback is the project rate) and Sony (the M01.XML file next to the clip). Canon shows only the playback rate for now (a metadata sample is missing), as does other video (iPhone …). Duration = number of frames ÷ playback rate, i.e. the clip's length in the edit (for 35 fps in a 24 project longer than the real shooting time). Under the table is a line with the proxy settings, e.g. “Proxies: H.264 (h264_nvenc), 1080p, crop 1.85, LUT: automatic by camera → _PROXY/ · also in the folder G:\Proxy”.
  • All files: every file with its size, checksum (with MD5 also an md5 column) and status on each destination (verified, written, ERROR, not processed). In the HTML the list is collapsed, in the PDF expanded.
  • A list of skipped system files and, in the footer, the app version.

Pause

Pause on a running card lets the step in progress finish — a file or a clip — and only then stops the job; the button changes to Resume, which carries on smoothly with the next file or clip (nothing finished is repeated, the job is not restarted). Nothing is cancelled or deleted by it:

  • The copy finishes the file in progress on all destinations at once (the card is read only once); verification finishes reading the file it is reading (including the background reads of Verify-in-Proxy). Meanwhile the job card shows “Pausing (finishing file A001C003.mxf…)” and the speeds keep running — with a large file (ARRIRAW 100+ GB) this may take several minutes. Then “Paused — Resume continues with the next file.”, the speeds show “—” and the time estimate disappears. Before the copy stops, mmMover flushes the write cache of the destination disks and writes the records of the finished files: everything copied up to that moment really is on the disks, and after a crash or the computer turning off it is not copied again. During the pause no half-written .offload-part file is open (with Copy again, finished copies wait under a hidden name until the end of the copy; if the computer goes down in the meantime, the next repair overwrites them).
  • Clip analysis and proxies finish the clip in progress (“Pausing (finishing the proxy of clip A003…)”) — ffmpeg is never suspended or interrupted in the middle of its work. Likewise the PDF and the day report finish and the pause comes only before them.
  • Only the time when the job really stood still is left out of the speeds and times in the report and out of “Total” on the card; the time spent finishing a file is work. After Resume the speed is measured again.
  • The stuck-disk watchdog does not step in during a pause: a stopped job reads nothing, and a file that is still being finished keeps being read. But when a disk really gets stuck while the background verification is being finished, mmMover gives up on it after the limit (its files fail with a note about an unresponsive disk, never green) and the job stops — it does not hang in the “Pausing” state.
  • When you swap the card during “Pausing” or the pause and press Resume, mmMover always checks again which card is in the reader before the next file (even if the job had not stopped yet).
  • During a pause the computer does not go to sleep (sleep could damage open files on a USB disk). A paused job blocks the queue — the next card waits.
  • Cancel and closing the app during a pause — even in the “Pausing” state — end the job immediately, as without a pause: they do not wait for the file to finish, and the files in progress are deleted. Only when mmMover is just flushing the write cache of the destination disks (right before “Paused”, and at the end of the copy) does it wait for the disks to finish writing — usually a few seconds.
  • When you disconnect a destination disk during a pause, after Resume the files on that disk fail (the other destinations carry on) and the job card turns yellow — then Copy again helps.
  • When you swap or pull out the card during a pause, after Resume mmMover copies nothing more and the job card turns yellow: “The card in the reader was swapped or removed while paused — the remaining files were not copied. Insert the original card and append to the backup.” What was copied stays and is verified.
  • An append keeps its backup locked even during a pause: no other job can append to it in the meantime.

Copy again

A yellow card (some files do not match or failed) has the Copy again button. It starts the job “A001 · repair”, which copies again only the files that do not match, and only to the disks where they do not match — with the same settings as the original job and always with verification:

  • The button is shown only on a finished job (not a cancelled one), when the same card is in the reader and no repair of the same backup is already waiting or running.
  • A good copy is never overwritten: on a disk where the file is fine, it is only read again and compared with the recorded checksum.
  • A mismatched copy is not deleted: before the new copy it is moved to _REPORT\neshoda_0002\… in the card folder (the number is the repair's generation, chapter 10; when the place is taken, the first free one is used, e.g. neshoda_0002_2). You can delete it by hand once you have verified the backup.
  • The file on the card must have the same size, time and checksum as at the first copy — when the card has changed in the meantime, the repair writes nothing and the recorded checksum stays (“Repair stopped — nothing was copied. …”, chapter 12).
  • The repair writes a new generation of the report and ASC MHL to all destinations (like an append), and rewrites the checksum lists, clip lists and the day report. The card's history is corrected — after a successful repair the card's line says “— verified, safe to format” again. Clip analysis and proxies are not repeated.
  • When there is nothing to repair: “Nothing to repair — all files are fine on all destinations.” An interrupted repair spoils nothing — start it again.
  • A repair is always verified by read-back, even when the original job ran without verification; good copies that have not been read back yet (cancelled verification, a backup without verification) are read too — with a large card this may take a while. When something is still unverified after the repair, the card stays yellow and mmMover says so.
  • A repair and an append of the same backup never run at the same time (“Another job is working with this backup right now — an append, a repair or a verification during proxies (…) — wait until it finishes.”). A repair cannot be started from the command line.

When any job ends, mmMover's button in the Windows taskbar flashes; on an error, an error sound plays. A finished card appears in the TODAY overview under the queue and in the Card history tab.

Notifications

When the mmMover window is not in the foreground, Windows shows a notification at the end of a job (the mmMover icon appears in the notification area at the bottom right and stays there until the app is closed; clicking the notification or the icon brings the window back): “mmMover: A001 done” (“Verified on 2 disks — the card is safe to format. Proxies: 24 done.”), “mmMover: A001 — needs attention” (not verified, failed proxies, proxies skipped for lack of space…), “mmMover: A001 — ERROR” and, after the copy while the proxies are still being made and verification runs, “mmMover: A001 — safe to eject” (without a sound; not safe to format yet). A job that fails during the copy reports the error as soon as the copy ends. A cancelled job has no notification. The sound and the flashing button stay.

Settings → Notifications → Edit notifications…: Windows notifications (on) and Send to a phone via ntfy — to the ntfy app on your phone (the server https://ntfy.sh or your own; the topic may contain only letters without accents, digits, - and _). The Send a test notification button shows “Sent.” or “Failed: …” (after at most 10 s). Choose a topic that cannot be guessed — anyone who knows it can read the notifications. The phone gets a fixed text: the card name, the result and the counts (e.g. “Verified on 2 disks — the card is safe to format.”), for warnings and errors only a general sentence; never paths, file names or the computer's name, and “safe to eject” is not sent to the phone. A job never waits for the sending. The notification settings belong to the project.

Cards already backed up

When you start a full copy of a card the history knows, mmMover asks in the Cards already backed up window (for one card, Card already backed up) with a list of the backups and the folder that would be created (e.g. A001_2): Copy again in full, Skip backed-up (starts only the other cards) or Cancel (starts nothing). It does not ask for a card that has changed since the backup (its line already says that only a full copy is possible), for an empty card, or for cards with the append option ticked. The command line does not ask; it only prints a line with the backup.

Appending new clips

An append job is named “A001 · append” and uses the destinations of the earlier backup. It copies only new files, overwrites nothing and writes a new generation of the report and ASC MHL (chapter 10). When there is nothing to copy, it ends Done with the text “Nothing new — the backup is complete.” In orange it may warn “5 files of the earlier backup were not verified — Verify backup is recommended.” The append is refused before anything is written (a red message on the job card, chapter 12) when the earlier backup is unreachable, its report or ASC MHL is missing, the backups on the destinations are not the same, the card holds no file of the backup (a different card), there is a file with the same name but a different size or date, or another job is appending to the same backup right now (the same card folder is only ever appended to once at a time, even from a second mmMover window). Then make a full copy. When the card changed between ticking it and Start, Start says “Card A001 has changed — it can no longer be appended. Check it and start again.” and does not start that card (the others start).

Two card states and content defects

The job card shows two separate chips. Safe to eject (neutral): everything is written to all disks; you can remove the card and insert the next one. Safe to format (the only green one): everything is verified on all disks and the result is written in all folders. Do not format the card until it has the Safe to format chip. While verification runs, the chip shows Verifying…; when a file or disk failed, it shows Do not format.

Content defects. While making proxies the decoder sometimes finds a defect right in the camera file (a damaged frame, wrong timestamps, extra frames, a clip that ends early, damaged audio). The copy still matches the card, so the copy is fine — the defect is in the original. The clip gets a yellow label with the timecode of the spot (e.g. “01:00:02:13 · corrupt data”) and the Preview button opens an image of that spot. The chip changes to Safe to format after checking defects. When you have checked the defects, confirm them with the Checked — the card is safe to format button: only then do the chip and the card turn green. mmMover itself never formats the card.

A note about the cache. mmMover reads the copies from the disk bypassing the Windows cache. When the volume or file does not allow that (for example a file compressed by NTFS or encrypted with EFS), it is verified by reading through the cache and the card shows an orange note “Verified by reading through the Windows cache: … — the volume or the file does not allow reads past the cache, so the data may have come from memory instead of the disk.”. The copy counts as verified and the card is safe to format, but without the sound and with a needs attention notification; the most reliable choice is to back up to uncompressed and unencrypted folders.

Finish an interrupted backup

When the app crashes or the computer turns off in the middle of a copy or during verification with proxies, the backup stays unfinished: the history shows it as “Unfinished backup on … to … — the copy was interrupted; it can be finished”, the day report marks it VERIFYING or UNFINISHED, and Verify backup does not report a clean “Verified: all … files match” (on the command line it ends with code 1). Do not format the card. Insert the card again: it has the checkbox Finish interrupted backup (on the command line mmmover append); it is offered even when there is nothing new to copy and only the verification is missing. Finishing continues where the backup stopped: files that are already on the disks are not read from the card again, a half-written large file continues from the last checkpoint (every 1 GiB) and the verification runs to the end; the result is written in the same generation. Until the backup is finished, Copy again (repair) and further appends are refused, as is a parallel job on the same backup. Finished proxies are not rendered again.

A disk disconnected during verification. When a destination disk is disconnected during verification with proxies, its files end up “✕ read”, the card shows Do not format and the verification result is not written into its folder — the backup stays unfinished. Connect the disk, insert the card and first choose Finish interrupted backup: nothing is read from the card, the disk is read and verified. Only when some files then do not match, use Copy again (before that, the repair is refused with a pointer to finishing the backup).

Verifying a backup

Verify backup in the top bar (Ctrl+Shift+O; also in Settings → Verification) picks a card folder on a destination, or a whole day folder (each card is verified separately). Each verification is a queue item “Verification A001” and runs in the same queue as the copies, one after another (it loads the same disks): “Verifying 120 / 1,234 files · 45 GB / 512 GB · 380 MB/s”. The result in green “Verified: all 1,234 files match (ASC MHL, 2 generations, xxHash64).”, in red “Mismatch 2 files, missing 1, unreadable 0 — details in the verification report.”, in orange extra files, files that already failed during the copy, and changed MHL generations. The buttons Verification report and Open folder; Cancel ends the verification without a report. The verification report is saved as long as Save a verification report is ticked in Settings → Verification: into the card's _REPORT, and for a backup with an MHL from another program (one that does not ignore _REPORT) into a _REPORT next to the card folder, with the note “The verification report is saved outside the card folder so it does not disturb its ASC MHL history: …”. All ASC MHL generations and all of its checksums are verified (xxHash64, MD5, SHA-1, xxHash3, xxHash128, C4) — including backups from other programs; without ascmhl the check is against _REPORT\<card>.xxh64. Nothing is ever written to the card or into ascmhl during verification.

Cancelling

The Cancel button is on the job card while the job is waiting, running or paused. Files in progress (.offload-part) are deleted, finished ones stay. A cancelled job that had not started yet is simply marked Cancelled. If you cancel a job only during clip analysis or proxies, the card is already backed up and “safe to eject” still holds (format only after verification).

Closing the app during an offload

When you close the window with a job running, the app asks “An offload is running. Quit anyway? Files in progress are deleted, finished files stay.” After Yes all jobs are cancelled and the window closes once it has cleaned up (meanwhile “Closing — waiting for the cancelled jobs to clean up.”).

An interrupted card is not backed up Back up again, in full, a card whose copy was cancelled or interrupted by closing the app.

Ejecting the card

  • The Eject card button is on the green job card. The card in the reader is ejected as a medium, the reader stays connected. Then the job card says “Card ejected” and the card disappears from step 1 · CARDS.
  • Only the card that was copied is ejected. When you swap or pull out the card in the reader, the button disappears.
  • It is not ejected while another job is still copying from the card (“another job is still copying from the card — eject it when that copy finishes”).
  • Internal disks, the system disk, network folders and folders added by hand (not whole cards) are never ejected.
  • When ejecting fails, the app shows “Could not eject the card: …” with the reason (chapter 12).

Note: actually ejecting the card from the reader has not been tried on all readers yet. If the button does not work, use the Windows Safely Remove Hardware icon.

9Hardware: USB ports and the bottleneck

The speed of an offload is often limited not by the card or the disk but by the port, the cable or a shared USB controller. The Hardware window shows what is connected where and how fast, and advises what to reconnect. It runs only on request:

  • the Hardware button in the top bar or Ctrl+U,
  • Settings → App → Test USB ports….

The test covers the ticked cards and destinations. When no card or destination is selected, it checks all connected disks. The quick check takes seconds and writes nothing. The result is shown by the dot on the Hardware button: green = no warnings, yellow = there are recommendations (the tooltip says how many and when).

Measuring speed

  • The app asks before measuring. The cards are only read (up to 1 GB from each). A temporary 1 GB file is written to and read from each destination disk and deleted right away. Depending on the disk speed this may take several minutes.
  • A speed test is possible only when a card is selected or a destination added (otherwise “To measure, select a card or add a destination.”).
  • It is not possible during copying (“Cannot measure while copying — the measurement writes 1 GB to the destination disks.”). Conversely, an offload cannot be started during a speed test (“A speed measurement is running — wait or stop it”).
  • Stop ends the test and deletes the temporary file; what has been measured so far is shown.

Port names

Windows does not know where a port physically is on the computer. The app labels ports e.g. “port 6”, a port behind a hub “port 7 › 2”, and with several controllers adds the controller name (“Intel USB 3.20 xHCI · port 3”). Type your own name into the field next to the port (e.g. “front left”) — it is then used everywhere: in the disk lines, in the recommendations and in the tooltips of the speed table on the job card. The name is saved.

Bottleneck during the copy

During copying the job card shows a speed table — Card read and each destination in MB/s; the row's tooltip shows the device and the connection (e.g. “Card … — USB 3 (5 Gb/s), port 6”). Under the card is a sentence:

Bottleneck: the card reader (USB 3 (5 Gb/s)). The disks could do more.
Bottleneck: disk SHUTTLE_B (USB 2.0 (480 Mb/s) — the link is saturated). The card could be read faster.
  • The bottleneck is whatever slows the copy down: the card (reader) or one of the destinations. It is found by which disk has the most data waiting to be written, not by the momentary speed — in a copy the card and the disks all run at the same pace.
  • When the link is more than 85 % busy, the link shows “— the link is saturated”: a faster port or cable will help.
  • The sentence is not shown during a pause or verification. The link load in percent and the total per controller are shown in the Hardware window.

Windows cannot tell USB 10 and 20 Gb/s apart; both are shown as “USB 3 (10 Gb/s or more)”.

Good to know

  • The same card a second time on the same day → A001_2, A001_3… An earlier offload is not overwritten.
  • The files' modification date and time on the destination are the same as on the card.
  • A hidden file .<name>.offload-part means an unfinished write. After a cancelled or interrupted copy none should remain; if you find one, the copy of that file is not finished. Show hidden files in File Explorer via View → Show → Hidden items.
  • The final file name means “fully written”. What is verified is what the report marks as verified.
  • The _REPORT, _PROXY and ascmhl folders are not part of the card and are not counted in the MHL.
  • The format is the same as in the Mac version (still called Offload) — a copy can be verified on either.
  • An append writes only new files into the card folder and adds a report with a generation number (_0002) to the existing reports; the original reports and MHL generations are never overwritten (only the chain ascmhl_chain.xml and the list A001.xxh64 change, always in one piece). The Mac version does not read generations, but verifies the appended files from the A001.xxh64 list. If an append were interrupted half-way so that the reports and MHL do not match, the next append is refused and the folder has to be repaired by hand; a full copy into a new folder is always possible.
  • Copy again (repair) writes a generation just like an append: the files copied again and the good copies it only read are in the new MHL generation and in the _0002 report. Before that it moves the mismatched copy to _REPORT\neshoda_0002\ with the same path as on the card — nothing is deleted. The _REPORT folder is not part of the MHL, so the set-aside copy does not disturb verification.
  • The verification report goes only into _REPORT (for a foreign MHL that does not ignore _REPORT, into a _REPORT next to the card folder); nothing is ever written into ascmhl.
  • _REPORT in the day folder belongs to the day report (and to verification reports of foreign backups); a card therefore cannot have that name. The day report and the clip lists are derived from the card reports — they are rewritten as a whole and can be made again at any time (Day report… under the queue).
Verifying a copy later You can verify a finished copy against ASC MHL again at any time: Verify backup in the top bar (chapter 8), or bin\mmmover.exe verify D:\Backup\2026-10-06\A001 (chapter 11).

append options

mmmover append <card> has the same analysis, proxy and output options as copy (--no-analyze, --proxy, --lut, --ale, --no-day-report …; the checksums are set by the earlier backup, so it has no --hash) and in addition --into <card folder> (repeat it for every destination of the earlier backup; without it the folders are found in the history, otherwise “Error: The card is not in the history — give the backup folders with --into.”), --no-verify, --dry-run (prints a plan that a real run may still refine) and --no-history (then --into is required). Code 0 = appended (or “Nothing new — the backup is complete.”), 1 = refused or error, with the reason.

During and after the copy

  • Before the copy, the plan, a Connections: list (D1 = Destination 1: …) and connection warnings are printed. The status line shows which link is the bottleneck: bottleneck: D1, bottleneck: card, possibly (link full).
  • Ctrl+C cancels the copy: it finishes the current block and deletes the files in progress.
  • Exit code: 0 = all fine and the card is safe to format, 1 = error, or the card is not safe to format (the verification result could not be written into all folders, earlier unverified files; with --no-verify it stays 0 as before). Suitable for scripts. append also accepts --classic-verify and --primary.
  • For a card the history knows, copy prints before the plan Backed up on 2026-10-06 08:15 to D:\Backup, F:\Backup — verified, safe to format (without asking).
  • At the end, copy and append print Day report: D:\Backup\2026-10-06\_REPORT\2026-10-06_day_report.html for every destination.
  • For problem files verify prints MISMATCH (different checksum), MISSING (missing), ERROR (unreadable), EXTRA (not in the record), FAILED-AT-COPY (already failed during the copy), FAILED-SUPERSEDED (the newest record failed, the file matches an older generation), CHAIN (an ASC MHL chain problem) and at the end a summary: “Verified 1,234 files (512 GB) in 22:10 (385 MB/s) — all OK.” or “… — PROBLEMS FOUND: mismatch 2, missing 1, unreadable 0, failed during the copy 0, extra 3.” Code 1 on any problem (extra files alone do not count).

Frequently asked questions

Can I copy several cards at once?

Yes. Tick them all and start; they are copied one after another, and the proxies of the previous card run in parallel with the copy of the next one.

Do I need two destinations?

No, but with one destination the app warns that two independent copies are recommended.

How do I verify a backup later, for example after the disk has been transported?

Verify backup in the top bar, or bin\mmmover.exe verify <destination>\<date>\<card>. The ascmhl verify tool reports false “new/missing file” on Windows because of the slashes in paths — run a full ascmhl verify on macOS or Linux; on Windows use mmmover verify.

Does the Mac version (still called Offload) verify a copy made on Windows?

Yes, both versions write the same format (checksum list, report, MHL).
